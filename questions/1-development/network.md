### T01-Q01
*домен: офіційна мітка*

A company's e-commerce application becomes slow when traffic spikes. The application has a three-tier architecture (web, application and database tier) that uses synchronous transactions. The development team at the company has identified certain bottlenecks in the application tier and it is looking for a long term solution to improve the application's performance.

As a developer associate, which of the following solutions would you suggest to meet the required application response times while accounting for any traffic spikes?

- ▫️ Leverage SQS with asynchronous AWS Lambda calls to decouple the application and data tiers
- ▫️ Leverage horizontal scaling for the application's persistence layer by adding Oracle RAC on AWS
- ✅ Leverage horizontal scaling for the web and application tiers by using Auto Scaling groups and Application Load Balancer
- ▫️ Leverage vertical scaling for the application instance by provisioning a larger Amazon EC2 instance size

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Leverage horizontal scaling for the web and application tiers by using Auto Scaling groups and Application Load Balancer»**

Горизонтально масштабована система збільшує потужність, додаючи нові комп'ютери. Вертикально масштабована обмежена одним комп'ютером: продуктивність там можна підняти лише швидшими (або додатковими) CPU, пам'яттю чи сховищем. Горизонтальні системи часто працюють краще, бо виконують навантаження паралельно на багатьох машинах.

Elastic Load Balancing автоматично розподіляє вхідний трафік між усіма запущеними EC2-інстансами, щоб жоден з них не перевантажувався. Балансер прикріплюють до Auto Scaling group, і він стає єдиною точкою входу для всього веб-трафіку групи. Окремо реєструвати інстанси не треба: ті, що запускає ASG, реєструються в балансері автоматично, а ті, що термінуються, автоматично знімаються з реєстрації.

Цей варіант майже не змінює архітектуру — переважно це конфігурація, плюс здатність веб- і прикладного рівнів працювати на кількох інстансах. Тому він найкраще підходить.

**❌ Неправильні варіанти:**
- *Leverage SQS with asynchronous AWS Lambda calls to decouple the application and data tiers* — тут асинхронні виклики Lambda, а застосунок використовує синхронні транзакції. До того ж за умовою архітектура застосунку не має змінюватися.
- *Leverage horizontal scaling for the application's persistence layer by adding Oracle RAC on AWS* — проблема взагалі не в рівні зберігання даних; це дистрактор. (Oracle RAC — кластерна БД, де одну базу одночасно обслуговують кілька серверів.)
- *Leverage vertical scaling … larger Amazon EC2 instance size* — вертикальне масштабування лише тимчасово латає проблему і не працює в довгостроковій перспективі.

Джерела: <https://docs.aws.amazon.com/autoscaling/ec2/userguide/autoscaling-load-balancer.html> · <https://aws.amazon.com/blogs/compute/operating-lambda-understanding-event-driven-architecture-part-1/>

</details>

### T01-Q27
*домен: офіційна мітка*

A developer has created a new Application Load Balancer but has not registered any targets with the target groups.

Which of the following errors would be generated by the Load Balancer?

- ▫️ HTTP 502: Bad gateway
- ▫️ HTTP 500: Internal server error
- ✅ HTTP 503: Service unavailable
- ▫️ HTTP 504: Gateway timeout

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «HTTP 503: Service unavailable»**

Балансер повертає HTTP 503, коли в його target groups немає зареєстрованих цілей.

**❌ Неправильні варіанти:**
- *HTTP 500: Internal server error* — внутрішня помилка самого балансера або бекенду.
- *HTTP 502: Bad gateway* — ціль повернула некоректну відповідь або закрила з'єднання.
- *HTTP 504: Gateway timeout* — ціль не відповіла вчасно.

### T02-Q17
*домен: визначено автоматично (у джерелі: AWS Networking & Content Delivery)*

An organization is hosting a website on an Amazon EC2 instance in a public subnet. The website should allow public access for HTTPS traffic on TCP port 443 but should only accept SSH traffic on TCP port 22 from a corporate address range accessible over a VPN.

Which security group configuration will support both requirements?

- ▫️ Allow traffic to both port 443 and port 22 from 0.0.0.0/0 and 192.168.0.0/16.
- ✅ Allow traffic to port 443 from 0.0.0.0/0 and allow traffic to port 22 from 192.168.0.0/16.
- ▫️ Allow traffic to port 22 from 0.0.0.0/0 and allow traffic to port 443 from 192.168.0.0/16.
- ▫️ Allow traffic to both port 443 and port 22 from the VPC CIDR block.

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Allow traffic to port 443 from 0.0.0.0/0 and allow traffic to port 22 from 192.168.0.0/16»**

Доступ до порту 443 з 0.0.0.0/0 відкриває сайт для всього інтернету. Обмеження порту 22 діапазоном 192.168.0.0/16 дозволяє SSH лише з корпоративної мережі (через VPN).

**❌ Неправильні варіанти:**
- *Port 22 from 0.0.0.0/0 and port 443 from 192.168.0.0/16* — навпаки: SSH відкрито всьому інтернету, а сайт — лише корпоративній мережі.
- *Both ports from the VPC CIDR block* — ні користувачі з інтернету не відкриють сайт, ні корпоративні користувачі не зайдуть по SSH.
- *Both ports from 0.0.0.0/0 and 192.168.0.0/16* — SSH не обмежено корпоративним діапазоном.

Джерела: <https://docs.aws.amazon.com/vpc/latest/userguide/VPC_SecurityGroups.html>

</details>

- ▫️ Create a Web ACL in AWS Shield with a rule that matches the specified countries and blocks access.

### T02-Q43
*домен: визначено автоматично (у джерелі: AWS Database)*

> ⚠️ **Сесії → DynamoDB (бо серед варіантів немає ElastiCache; ключ — "не втратити").** → [детальніше](../../06-contradictions-and-traps.md#c01)

A Developer is designing a fault-tolerant application that will use Amazon EC2 instances and an Elastic Load Balancer. The Developer needs to ensure that if an EC2 instance fails session data is not lost. How can this be achieved?

- ✅ Use Amazon DynamoDB to perform scalable session handling
- ▫️ Use an EC2 Auto Scaling group to automatically launch new instances
- ▫️ Enable Sticky Sessions on the Elastic Load Balancer
- ▫️ Use Amazon SQS to save session data

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Use Amazon DynamoDB to perform scalable session handling»**

Головна вимога — не втратити дані, тож вони мають жити в довговічному сховищі поза EC2. DynamoDB для цього підходить: для багатьох мов є готові session handlers (наприклад, DynamoDB Session Handler для PHP). Він переносить сесії з локальної файлової системи в спільне місце; DynamoDB швидка, масштабована, проста в налаштуванні й автоматично реплікує дані.

**❌ Неправильні варіанти:**
- *Sticky Sessions on ELB* — повертають користувача на той самий інстанс, але не гарантують збереження сесії, якщо він впаде.
- *EC2 Auto Scaling group* — замінює інстанси, але не зберігає сесії.
- *Amazon SQS* — не підходить для зберігання сесій.

Джерела: <https://docs.aws.amazon.com/aws-sdk-php/v2/guide/feature-dynamodb-session-handler.html>

</details>

### T02-Q57
*домен: визначено автоматично (у джерелі: AWS Database)*

A web application runs on a fleet of Amazon EC2 instances in an Auto Scaling group behind an Application Load Balancer (ALB). A developer needs a store for session data so it can be reliably served across multiple requests.

Where is the best place to store the session data?

- ▫️ Write the data to the local instance store volumes.
- ▫️ Write the data to the root of the filesystem.
- ▫️ Write the data to a shared Amazon EBS volume.
- ✅ Write the data to an Amazon ElastiCache cluster.

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Write the data to an Amazon ElastiCache cluster»**

ElastiCache добре підходить для сесій: дуже низька затримка й висока продуктивність (для того ж часто використовують DynamoDB). Сесію, записану в кластер, легко прочитати з того ж або іншого EC2-інстансу. Дані відв'язані від інстансу, тож при його падінні не губляться.

**❌ Неправильні варіанти:**
- *Shared Amazon EBS volume* — EBS ділити між інстансами можна лише в особливих випадках, і він усе одно залежить від інстансу, який може впасти.
- *Root of the filesystem* та *Local instance store volumes* — дані зникнуть разом з інстансом.

### T03-Q38
*домен: офіційна мітка*

Your company manages MySQL databases on EC2 instances to have full control. Applications on other EC2 instances managed by an ASG make requests to these databases to get information that displays data on dashboards viewed on mobile phones, tablets, and web browsers.

Your manager would like to scale your Auto Scaling group based on the number of requests per minute. How can you achieve this?

- ▫️ Attach an Elastic Load Balancer
- ✅ You create a CloudWatch custom metric and build an alarm to scale your ASG
- ▫️ You enable detailed monitoring and use that to scale your ASG
- ▫️ Attach additional Elastic File Storage

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «You create a CloudWatch custom metric and build an alarm to scale your ASG»**

Масштабувати треба за кількістю запитів на хвилину, а такої метрики в CloudWatch за замовчуванням немає. Тож створюють custom metric (standard або high resolution; high resolution зберігається з точністю 1 с і читається з періодом 1, 5, 10, 30 с або кратним 60 с) і alarm, що запускає масштабування ASG.

**❌ Неправильні варіанти:**
- *Attach an Elastic Load Balancer* — балансер розподіляє навантаження і перевіряє здоров'я, але не змінює кількість інстансів.
- *Attach additional EFS* — спільна файлова система, до автомасштабування відношення не має.
- *Enable detailed monitoring* — дає стандартні метрики EC2 щохвилини, але не кількість запитів застосунку.

</details>

### T03-Q43
*домен: офіційна мітка*

You are designing a high-performance application that requires millions of connections. You have several EC2 instances running Apache2 web servers and the application will require capturing the user’s source IP address and source port without the use of X-Forwarded-For.

Which of the following options will meet your needs?

- ▫️ Elastic Load Balancer
- ▫️ Classic Load Balancer
- ✅ Network Load Balancer
- ▫️ Application Load Balancer

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Network Load Balancer»**

NLB працює на 4-му рівні OSI і обробляє мільйони запитів на секунду. Отримавши з'єднання, він вибирає ціль і відкриває до неї TCP-з'єднання. Вхідні з'єднання не змінюються, тож IP і порт клієнта видно без `X-Forwarded-For`.

**❌ Неправильні варіанти:**
- *Application Load Balancer* — 7-й рівень, маршрутизація за правилами (path-based тощо); IP клієнта передає через X-Forwarded-For.
- *Elastic Load Balancer* — це назва самого сервісу з кількома типами балансерів.
- *Classic Load Balancer* — базовий балансер старого покоління.

</details>

### T03-Q48
*домен: офіційна мітка*

A developer is configuring an Application Load Balancer (ALB) to direct traffic to the application's EC2 instances and Lambda functions.

Which of the following characteristics of the ALB can be identified as correct? (Select two)

- ▫️ An ALB has three possible target types: Hostname, IP and Lambda
- ✅ An ALB has three possible target types: Instance, IP and Lambda
- ▫️ If you specify targets using an instance ID, traffic is routed to instances using any private IP address from one or more network interfaces
- ✅ You can not specify publicly routable IP addresses to an ALB
- ▫️ If you specify targets using IP addresses, traffic is routed to instances using the primary private IP address

<details><summary>Пояснення</summary>

**✅ Правильні відповіді: «An ALB has three possible target types: Instance, IP and Lambda» та «You can not specify publicly routable IP addresses to an ALB»**

Тип target group задається при створенні й потім не змінюється:
- **Instance** — ціль за instance ID;
- **IP** — ціль за IP-адресою;
- **Lambda** — ціль — Lambda-функція.

Для типу IP можна вказати лише адреси з певних (приватних) CIDR-діапазонів; публічні маршрутизовані IP — ні.

**❌ Неправильні варіанти:**
- *Instance ID → any private IP from network interfaces* — навпаки: за instance ID трафік іде на primary private IP основного інтерфейсу.
- *IP targets → primary private IP* — навпаки: за IP можна направити трафік на будь-яку приватну IP інстансу (кілька застосунків на одному порту).
- *Hostname, IP and Lambda* — типу Hostname немає.

</details>

### T03-Q54
*домен: офіційна мітка*

A firm maintains a highly available application that receives HTTPS traffic from mobile devices and web browsers. The main Developer would like to set up the Load Balancer routing to route traffic from web servers to smart.com/api and from mobile devices to smart.com/mobile. A developer advises that the previous recommendation is not needed and that requests should be sent to api.smart.com and mobile.smart.com instead.

Which of the following routing options were discussed in the given use-case? (select two)

- ▫️ Cookie value
- ✅ Path based
- ▫️ Client IP
- ▫️ Web browser version
- ✅ Host based

<details><summary>Пояснення</summary>

**✅ Правильні відповіді: «Path based» та «Host based»**

- **Path-based routing:** правила listener'а за URL-шляхом. Наприклад, `/api` — в одну target group, `/mobile` — в іншу (і для кожної можна обрати свій тип інстансів).
- **Host-based routing:** правила ALB за доменом із заголовка Host: `api.example.com` — в одну target group, `mobile.example.com` — в іншу, решта — за правилом за замовчуванням. Обидва способи можна комбінувати (`api.example.com/production` і `/sandbox`).

**❌ Неправильні варіанти:**
- *Client IP* — дистрактор (у банку; насправді ALB має умову source-ip, але в сценарії її немає).
- *Web browser version* — маршрутизація не залежить від браузера.
- *Cookie value* — у сценарії не йдеться про маршрутизацію за cookies.

</details>

### T03-Q55
*домен: офіційна мітка*

You have configured a Network ACL and a Security Group for the load balancer and Amazon EC2 instances to allow inbound traffic on port 80. However, users are still unable to connect to your website after launch.

Which additional configuration is required to make the website accessible to all users over the internet?

- ▫️ Add a rule to the Network ACLs to allow outbound traffic on ports 1025 - 5000
- ✅ Add a rule to the Network ACLs to allow outbound traffic on ports 1024 - 65535
- ▫️ Add a rule to the Security Group allowing outbound traffic on port 80
- ▫️ Add a rule to the Network ACLs to allow outbound traffic on ports 32768 - 61000

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Add a rule to the Network ACLs to allow outbound traffic on ports 1024 - 65535»**

Network ACL — необов'язковий рівень захисту VPC, фаєрвол на рівні підмереж. Користувацький NACL за замовчуванням забороняє весь вхідний і вихідний трафік, поки не додати правила. NACL **stateless**: відповіді на дозволений вхідний трафік підпадають під правила вихідного (і навпаки).

Діапазон ephemeral-портів обирає клієнт, і він залежить від ОС:
- Linux (зокрема Amazon Linux) — 32768–61000;
- **запити від Elastic Load Balancing — 1024–65535**;
- Windows до Server 2003 — 1025–5000;
- Windows Server 2008+ — 49152–65535;
- NAT gateway і Lambda — 1024–65535.

**❌ Неправильні варіанти:**
- *Outbound 1025 – 5000* — це діапазон старих Windows, а ELB використовує 1024–65535.
- *Outbound 32768 – 61000* — діапазон Linux, а ELB використовує 1024–65535.
- *Security Group outbound on port 80* — SG stateful: відповіді на дозволений вхідний трафік виходять незалежно від outbound-правил.

Джерела: <https://docs.aws.amazon.com/vpc/latest/userguide/vpc-network-acls.html> · <https://docs.aws.amazon.com/vpc/latest/userguide/VPC_SecurityGroups.html>

</details>

A Developer is creating an application that uses Amazon EC2 instances and must be highly available and fault tolerant. How should the Developer configure the VPC?

- ✅ Create a subnet in each availability zone in the region
- ▫️ Create an Internet Gateway for every availability zone
- ▫️ Create a cluster placement group for the EC2 instances
- ▫️ Create multiple subnets within a single availability zone in the region

<details><summary>Пояснення</summary>

- *Multiple subnets within a single AZ* — при недоступності AZ відмовостійкості не буде.

- *Cluster placement group* — для низької затримки між інстансами в одній AZ.

### T04-Q48
*домен: визначено автоматично (у джерелі: AWS Compute)*

An application includes multiple Auto Scaling groups of Amazon EC2 instances. Each group corresponds to a different subdomain of example.com, including forum.example.com and myaccount.example.com. An Elastic Load Balancer will be used to distribute load from a single HTTPS listener.

Which type of Elastic Load Balancer MUST a Developer use in this scenario?

- ✅ Application Load Balancer
- ▫️ Network Load Balancer
- ▫️ Task Load Balancer
- ▫️ Classic Load Balancer

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Application Load Balancer»**

A company runs an application on a fleet of web servers running on Amazon EC2 instances. The web servers are behind an Elastic Load Balancer (ELB) and use an Amazon DynamoDB table for storing session state. A Developer has been asked to implement a mechanism for automatically deleting session state data that is older than 24 hours.

What is the SIMPLEST solution to this requirement?

- ▫️ Each day, create a new table to hold session data; delete the previous day's table
- ▫️ Write a script that deletes old records; schedule the scripts as a cron job on an Amazon EC2 instance
- ▫️ Add an attribute with the expiration time; name the attribute ItemExpiration
- ✅ Add an attribute with the expiration time; enable the Time To Live feature based on that attribute

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Add an attribute with the expiration time; enable the Time To Live feature based on that attribute»**

TTL у DynamoDB визначає, коли елемент «протухає» і автоматично видаляється. Час видалення задається для кожного елемента окремо. Це корисно для даних, що з часом втрачають цінність (сесії, логи подій), і для даних, які за вимогами регуляторів можна зберігати лише певний час.

- Фоновий процес порівнює поточний час (epoch) зі значенням атрибута типу Number.
- Елемент видаляється, якщо значення в epoch-форматі, менше за поточний час і не старше 5 років.

Тож треба додати атрибут із часом спливання в epoch-форматі й увімкнути TTL на цьому атрибуті.

**❌ Неправильні варіанти:**
- *New table each day* — видалятиме й дані, молодші за 24 години, бо запускається в певний час.
- *Cron script on EC2* — неелегантно й дорожче: видалення споживають WCU.
- *Attribute named ItemExpiration* — неповне рішення: TTL на таблиці теж треба ввімкнути.
