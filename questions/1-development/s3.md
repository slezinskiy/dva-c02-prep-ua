### T01-Q25
*домен: офіційна мітка*

> ⚠️ **Застаріле: S3 Select закритий для нових клієнтів (2024) → Athena.** → [детальніше](../../07-outdated-and-wrong-answers.md#o04)

You would like to retrieve a subset of your dataset stored in S3 with the CSV format. You would like to retrieve a month of data and only 3 columns out of the 10.

You need to minimize compute and network costs for this, what should you use?

- ▫️ S3 Access Logs
- ✅ S3 Select
- ▫️ S3 Inventory
- ▫️ S3 Analytics

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «S3 Select»**

S3 Select дає змогу простими SQL-виразами отримати лише частину даних з об'єкта. Застосунок забирає тільки потрібне, що часто дає до 400% приросту продуктивності та економить обчислення й мережу. (Зауваж: S3 Select закрито для нових клієнтів, сучасна альтернатива — Athena.)

**❌ Неправильні варіанти:**
- *S3 Inventory* — звіти про стан реплікації та шифрування об'єктів для аудиту й compliance.
- *S3 Analytics* — аналіз патернів доступу, щоб вирішити, коли переводити дані з STANDARD у STANDARD_IA.
- *S3 Access Logs* — детальні записи запитів до бакета для аудиту безпеки та аналізу витрат.

</details>

### T01-Q26
*домен: офіційна мітка*

A company ingests real-time data into its on-premises data center and subsequently a daily data feed is compressed into a single file and uploaded on Amazon S3 for backup. The typical compressed file size is around 2 GB.

Which of the following is the fastest way to upload the daily compressed file into S3?

- ▫️ Upload the compressed file in a single operation
- ▫️ FTP the compressed file into an EC2 instance that runs in the same region as the S3 bucket. Then transfer the file from the EC2 instance into the S3 bucket
- ✅ Upload the compressed file using multipart upload with S3 transfer acceleration
- ▫️ Upload the compressed file using multipart upload

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Upload the compressed file using multipart upload with S3 transfer acceleration»**

S3 Transfer Acceleration пришвидшує передачу файлів на великі відстані між клієнтом і бакетом. Дані надходять у найближчу edge-локацію CloudFront, а звідти йдуть до S3 оптимізованим мережевим маршрутом.

Multipart upload завантажує об'єкт частинами — незалежно, в будь-якому порядку і паралельно. Якщо частина не дійшла, повторно передають лише її. На стабільній швидкій мережі це максимально використовує пропускну здатність, на нестабільній — підвищує стійкість до збоїв.

**❌ Неправильні варіанти:**
- *Upload in a single operation* — для об'єктів від 100 MB варто використовувати multipart upload: паралельні частини дають кращу пропускну здатність.
- *Upload using multipart upload* (без acceleration) — швидше, ніж одним запитом, але разом із Transfer Acceleration швидкість ще вища.
- *FTP the file into an EC2 instance, then to S3* — обхідний шлях, який вимагає багато скриптів і точно не найшвидший. Дистрактор.

Джерела: <https://docs.aws.amazon.com/AmazonS3/latest/dev/transfer-acceleration.html> · <https://docs.aws.amazon.com/AmazonS3/latest/dev/uploadobjusingmpu.html>

</details>

<a id="t01-q54"></a>
### T01-Q54
*домен: офіційна мітка*

Your organization has a single Amazon Simple Storage Service (S3) bucket that contains folders labeled with customer names. Several administrators have IAM access to the S3 bucket and versioning is enabled to easily recover from unintended user actions.

Which of the following statements about versioning is NOT true based on this scenario?

- ✅ Versioning can be enabled only for a specific folder
- ▫️ Any file that was unversioned before enabling versioning will have the 'null' version
- ▫️ Overwriting a file increases its versions
- ▫️ Deleting a file is a recoverable operation

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Versioning can be enabled only for a specific folder»** (питання про НЕправильне твердження)

Стан версіонування застосовується до всіх (а не до деяких) об'єктів бакета. Після першого ввімкнення versioning об'єкти завжди версіонуються й отримують унікальний version ID. Увімкнути версіонування лише для однієї «папки» неможливо, тож це твердження хибне.

**❌ Інші варіанти — правдиві твердження:**
- *Overwriting a file increases its versions* — перезапис створює нову версію, попередню можна відновити.
- *Deleting a file is a recoverable operation* — при видаленні S3 додає delete marker, і попередню версію можна відновити.
- *Any file that was unversioned before enabling versioning will have the 'null' version* — так, ці об'єкти мають version ID `null` і не змінюються.

</details>

### T02-Q42
*домен: визначено автоматично (у джерелі: AWS Analytics)*

A developer is running queries on Hive-compatible partitions in Athena using DDL but is facing time out issues. What is the most effective and efficient way to prevent this from continuing to happen?

- ✅ Use the MSCK REPAIR TABLE command to update the metadata in the catalog.
- ▫️ Use the ALTER TABLE ADD PARTITION command to update the column names.
- ▫️ Export the data into DynamoDB to perform queries in a more flexible schema.
- ▫️ Export the data into a JSON document to clean any errors and upload the cleaned data into S3.

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Use the MSCK REPAIR TABLE command to update the metadata in the catalog»**

`MSCK REPAIR TABLE` сканує S3 на Hive-сумісні партиції, додані після створення таблиці, порівнює їх із метаданими й додає нові до метаданих і таблиці Athena. Коли партицій кілька тисяч і DDL падає з таймаутом, ця команда працює краще.

**❌ Неправильні варіанти:**
- *ALTER TABLE ADD PARTITION to update the column names* — ця DDL-команда додає партиції, а не перейменовує колонки, і проблему таймаутів не вирішує.
- *Export the data into DynamoDB* — DynamoDB — NoSQL, це не рішення для Athena.
- *Export into JSON, clean, upload to S3* — неефективно і не вирішує таймаути DDL.

Джерела: <https://docs.aws.amazon.com/athena/latest/ug/msck-repair-table.html>

</details>

### T02-Q44
*домен: визначено автоматично (у джерелі: AWS Analytics)*

A developer is partitioning data using Athena to improve performance when performing queries. What are two things the analyst can do that would counter any benefit of using partitions? (Select TWO.)

- ▫️ Storing the data in S3.
- ▫️ Using a Hive-style partition format.
- ✅ Skewing data heavily to one partition value.
- ▫️ Creating partitions directly from data source.
- ✅ Segmenting data too finely.

<details><summary>Пояснення</summary>

**✅ Правильні відповіді: «Skewing data heavily to one partition value» та «Segmenting data too finely»**

Партиціювання має свою ціну. Більше партицій — більше накладних витрат на отримання й обробку метаданих партицій, а багато дрібних файлів зводить вигоду нанівець. Якщо дані сильно перекошені в одне значення партиції і більшість запитів його використовує, накладні витрати можуть з'їсти всю вигоду.

**❌ Неправильні варіанти:**
- *Storing the data in S3* — Athena й так працює з S3.
- *Creating partitions directly from data source* — Athena читає дані напряму з S3.
- *Using a Hive-style partition format* — Athena сумісна з Hive-партиціями.

Джерела: <https://aws.amazon.com/blogs/big-data/top-10-performance-tuning-tips-for-amazon-athena/>

</details>

### T03-Q26
*домен: офіційна мітка*

The development team at a company wants to insert vendor records into an Amazon DynamoDB table as soon as the vendor uploads a new file into an Amazon S3 bucket.

As a Developer Associate, which set of steps would you recommend to achieve this?

- ▫️ Set up an event with Amazon EventBridge that will monitor the S3 bucket and then insert the records into DynamoDB
- ▫️ Develop a Lambda function that will poll the S3 bucket and then insert the records into DynamoDB
- ✅ Create an S3 event to invoke a Lambda function that inserts records into DynamoDB
- ▫️ Write a cron job that will execute a Lambda function at a scheduled time and insert the records into DynamoDB

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Create an S3 event to invoke a Lambda function that inserts records into DynamoDB»**

S3 event notifications повідомляють про події в бакеті. Конфігурація вказує, які події публікувати й куди надсилати. Об'єкт створюють API PUT, POST, COPY; подія `s3:ObjectCreated:*` спрацьовує незалежно від API. Тут при PUT спрацьовує Lambda, яка записує дані в DynamoDB.

**❌ Неправильні варіанти:**
- *Cron job that executes a Lambda function* — неефективно: на момент запуску нових файлів може не бути.
- *EventBridge event that monitors the bucket and inserts records* — EventBridge не пише в DynamoDB напряму (це не підтримувана ціль), все одно знадобиться Lambda.
- *Lambda function that polls the bucket* — неефективно з тієї ж причини, що й cron.

</details>

### T03-Q41
*домен: офіційна мітка*

A developer is migrating an on-premises application to AWS Cloud. The application currently processes user uploads and uploads them to a local directory on the server. All such file uploads must be saved and then made available to all instances in an Auto Scaling group.

As a Developer Associate, which of the following options would you recommend for this use-case?

- ▫️ Use Instance Store type of EC2 instances and share the files via file synchronization software
- ▫️ Use Amazon EBS as the storage volume and share the files via file synchronization software
- ▫️ Use Amazon EBS and configure the application AMI to use a snapshot of the same EBS instance while launching new instances
- ✅ Use Amazon S3 and make code changes in the application so all uploads are put on S3

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Use Amazon S3 and make code changes in the application so all uploads are put on S3»**

Amazon S3 — надзвичайно довговічне, високодоступне й необмежено масштабоване об'єктне сховище за низьку ціну, з простим веб-інтерфейсом. Застосунок завантажує файли через `PutObject` в один бакет, і вони доступні з усіх інстансів ASG.

**❌ Неправильні варіанти:**
- *EBS + snapshot для нових інстансів* — EBS прив'язаний до одного інстансу, а snapshot перенесе на нові інстанси лише застарілі дані.
- *Instance Store / EBS + ПЗ для синхронізації файлів* — технічно можливо, але багато розробки і менш надійно, ніж S3.

</details>

### T04-Q10
*домен: визначено автоматично (у джерелі: AWS Storage)*

An organization has an Amazon S3 bucket containing premier content that they intend to make available to only paid subscribers of their website. The objects in the S3 bucket are private to prevent inadvertent exposure of the premier content to non-paying website visitors.

How can the organization provide only paid subscribers the ability to download the premier content in the S3 bucket?

- ▫️ Add a bucket policy that requires Multi-Factor Authentication for requests to access the S3 bucket objects
- ✅ Generate a pre-signed object URL for the premier content file when a paid subscriber requests a download
- ▫️ Enable server-side encryption on the S3 bucket for data protection against the non-paying website visitors
- ▫️ Apply a bucket policy that grants anonymous users to download the content from the S3 bucket

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Generate a pre-signed object URL for the premier content file when a paid subscriber requests a download»**

Приватні об'єкти S3 доступні лише власнику, але він може поділитися ними через **pre-signed URL**, підписаний його обліковими даними, з обмеженим у часі дозволом. При створенні вказують облікові дані, бакет, ключ об'єкта, HTTP-метод (GET для завантаження) і час дії. Хто має URL, той і отримує доступ, тож URL генерують лише для платних підписників.

**❌ Неправильні варіанти:**
- *Bucket policy that grants anonymous users download access* — завантажити зможуть усі.
- *Bucket policy requiring MFA* — дуже складно в керуванні; pre-signed URL значно простіше.
- *Server-side encryption* — шифрує at rest, але S3 розшифрує дані для будь-кого, хто має доступ.

Джерела: <https://docs.aws.amazon.com/AmazonS3/latest/dev/ShareObjectPreSignedURL.html>

</details>

### T04-Q23
*домен: визначено автоматично (у джерелі: AWS Storage)*

A company has a global presence and managers must submit large quantities of reporting data to an Amazon S3 bucket located in the us-east-1 region on weekly basis. Uploads have been slow recently, how can you improve data throughput and upload times?

- ▫️ Create an AWS Direct Connect connection from each remote office
- ▫️ Use an AWS Managed VPN
- ✅ Enable S3 Transfer Acceleration on the S3 bucket
- ▫️ Use S3 Multi-part upload

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Enable S3 Transfer Acceleration on the S3 bucket»**

Transfer Acceleration пришвидшує передачу файлів на великі відстані: дані приходять у найближчу edge-локацію CloudFront, а звідти йдуть у S3 оптимізованим маршрутом. Він корисний, коли клієнти з усього світу вантажать в один бакет, коли регулярно передаються гігабайти чи терабайти між континентами і коли пропускна здатність каналу використовується не повністю.

**❌ Неправильні варіанти:**
- *Use S3 multi-part upload* — паралельні частини допомагають, але Transfer Acceleration (через мережу CloudFront) дає значно більший ефект.
- *AWS Direct Connect from each office* — з'єднує дата-центр із найближчим регіоном AWS і дуже дорогий.
- *AWS Managed VPN* — зашифрований тунель у VPC, швидкість завантаження в S3 не покращує.

Джерела: <https://docs.aws.amazon.com/AmazonS3/latest/dev/transfer-acceleration.html>

</details>

### T04-Q24
*домен: визначено автоматично (у джерелі: AWS Networking & Content Delivery)*

A Developer is creating a serverless website with content that includes HTML files, images, videos, and JavaScript (client-side scripts).

Which combination of services should the Developer use to create the website?

- ▫️ Amazon ECS and Redis
- ▫️ AWS Lambda and Amazon API Gateway
- ▫️ Amazon EC2 and Amazon ElastiCache
- ✅ Amazon S3 and Amazon CloudFront

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Amazon S3 and Amazon CloudFront»**

S3 може хостити статичний сайт: сторінки зі статичним вмістом, іноді з клієнтськими скриптами. Бакет налаштовують як website (вмикають хостинг, задають права й index document) і завантажують туди вміст. Щоб наблизити вміст до користувачів, перед S3 ставлять CloudFront. Варіанти: REST endpoint S3 як origin з обмеженням доступу через OAI (зараз — OAC), website endpoint з публічним доступом або website endpoint з обмеженням за заголовком Referer.

**❌ Неправильні варіанти:**
- *Amazon EC2 and Amazon ElastiCache* — не serverless.
- *Amazon ECS and Redis* — теж не serverless; Redis — кеш перед БД, а не перед контейнером.
- *AWS Lambda and Amazon API Gateway* — serverless, але для HTML, зображень, відео й JS краще підходять S3 і CloudFront.

Джерела: <https://docs.aws.amazon.com/AmazonS3/latest/dev/WebsiteHosting.html>

</details>

### T04-Q51
*домен: визначено автоматично (у джерелі: AWS Application Integration)*

An application will ingest data at a very high throughput from several sources and stored in an Amazon S3 bucket for subsequent analysis. Which AWS service should a Developer choose for this requirement?

- ✅ Amazon Kinesis Data Firehose
- ▫️ Amazon Kinesis Data Analytics
- ▫️ Amazon S3 Transfer Acceleration
- ▫️ Amazon Simple Queue Service (SQS)

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Amazon Kinesis Data Firehose»** (зараз — Amazon Data Firehose)

Firehose — найпростіший спосіб надійно завантажувати потокові дані в data lakes, сховища та аналітичні інструменти: він приймає, трансформує і доставляє дані в S3, Redshift, Elasticsearch/OpenSearch і Splunk майже в реальному часі. Для S3 дані доставляються в бакет, а при ввімкненій трансформації сирі дані можна додатково зберегти в інший бакет. Firehose приймає великі обсяги з дуже високою пропускною здатністю.

**❌ Неправильні варіанти:**
- *S3 Transfer Acceleration* — прискорює завантаження в S3, але не приймає потокові дані.
- *Kinesis Data Analytics* — аналіз потокових даних у реальному часі; для завантаження в сховище простіший Firehose.
- *Amazon SQS* — потрібні producers і consumers, які завантажуватимуть дані в S3; Firehose робить це сам.

Джерела: <https://aws.amazon.com/kinesis/data-firehose/>

</details>

- *Block IPs in Security Groups* — security groups мають лише allow-правила, тож блокувати ними не можна; до того ж S3 за SG не стоїть.

Джерела: <https://docs.aws.amazon.com/AmazonS3/latest/dev/ShareObjectPreSignedURL.html>

### T12-Q05

A multi-national company maintains separate AWS accounts for different verticals in their organization. The project manager of a team wants to migrate the Elastic Beanstalk environment from Team A's AWS account into Team B's AWS account. As a Developer, you have been roped in to help him in this process.

Which of the following will you suggest?

- ▫️ Create a saved configuration in Team A's account and configure it to Export. Now, log into Team B's account and choose the Import option. Here, you need to specify the name of the saved configuration and allow the system to create the new application. This takes a little time based on the Regions the two accounts belong to
- ✅ Create a saved configuration in Team A's account and download it to your local machine. Make the account-specific parameter changes and upload to the S3 bucket in Team B's account. From Elastic Beanstalk console, create an application from 'Saved Configurations'
- ▫️ Create an export configuration from the Elastic Beanstalk console from Team A's account. This configuration has to be shared with the IAM Role of Team B's account. The import option of Team B's account will show the saved configuration, that can be used to create a new Beanstalk application
- ▫️ It is not possible to migrate Elastic Beanstalk environment from one AWS account to the other

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Create a saved configuration in Team A's account and download it to your local machine. Make the account-specific parameter changes and upload to the S3 bucket in Team B's account. From Elastic Beanstalk console, create an application from 'Saved Configurations'»**

1. Створити saved configuration в акаунті A.
2. Завантажити її на свій комп'ютер.
3. Змінити параметри, що залежать від акаунта: key pair, subnet ID, ім'я застосунку.
4. Завантажити файл у бакет S3 акаунта B.
5. В акаунті B створити застосунок із розділу Saved Configurations.

**❌ Неправильні варіанти:**
- *Export / Import* — прямого експорту й імпорту в Beanstalk немає.
- *Not possible* — неправда.
- *Share export with IAM Role* — суперечить описаному процесу.

### T12-Q10
*домен: офіційна мітка*

A developer hosts a static website in Amazon S3 behind an Amazon CloudFront distribution, using a custom domain that points to the CloudFront URL. The site is deployed through a CI/CD pipeline where the source stage is followed by a build stage that runs an AWS CodeBuild project defined by a buildspec.yml file. The buildspec builds the code and uploads the static files to the S3 bucket, and the updated content is visible both in the bucket and through the S3 website endpoint. However, the CloudFront domain continues to serve stale content.

What do you recommend to fix this issue?

- ✅ Invoke an Amazon CloudFront invalidation for the changed paths
- ▫️ Add a post-build step to resync the S3 bucket so the latest artifacts overwrite prior objects
- ▫️ Modify the S3 bucket’s cross-origin resource sharing (CORS) configuration to allow all origins and redeploy the files
- ▫️ Enable S3 bucket versioning and keep uploading files under the same keys so CloudFront eventually sees the latest version

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Invoke an Amazon CloudFront invalidation for the changed paths»**

Інвалідація прибирає вказані об'єкти з edge-кешів CloudFront, тож наступний запит піде в origin (S3) по свіжу версію. Можна вказати лише змінені файли або шаблони з `*` (`/images/*`, `/app/*.js`), а не очищати всю дистрибуцію. Оновлення з'являються одразу, незалежно від TTL. Перші 1 000 шляхів на місяць безкоштовні, далі — оплата за кожен шлях.

**❌ Неправильні варіанти:**
- *Modify CORS* — CORS керує тим, як браузер виконує крос-доменні запити; на кеш CloudFront не впливає.
- *Resync S3 bucket* — в S3 будуть нові файли, але CloudFront віддаватиме старі, доки не спливе TTL або не буде інвалідації.
- *S3 versioning, same keys* — CloudFront кешує за URL і query string, а не за version ID; старий об'єкт віддаватиметься до спливання TTL.

Джерела: <https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html?utm_source=chatgpt.com> · <https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation_Requests.html>

</details>
