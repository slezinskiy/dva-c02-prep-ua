### T01-Q33
*домен: офіційна мітка*

A security company is requiring all developers to perform server-side encryption with customer-provided encryption keys when performing operations in AWS S3. Developers should write software with C# using the AWS SDK and implement the requirement in the PUT, GET, Head, and Copy operations.

Which of the following encryption methods meets this requirement?

- ▫️ SSE-KMS
- ▫️ SSE-S3
- ✅ SSE-C
- ▫️ Client-Side Encryption

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «SSE-C»**

Захистити дані at rest в S3 можна так:
- **Server-side encryption** — S3 шифрує об'єкт перед записом на диск і розшифровує при завантаженні.
- **Client-side encryption** — ти шифруєш дані сам і завантажуєш уже зашифровані; процес, ключі й інструменти — на тобі.

Компанія хоче керувати ключами у своєму застосунку, а шифрування доручити S3. Це **SSE-C** (server-side encryption with customer-provided keys): ти передаєш ключ у кожному запиті, а S3 шифрує при записі й розшифровує при читанні.

**❌ Неправильні варіанти:**
- *SSE-KMS* — ключі зберігаються в AWS KMS (customer managed або AWS managed), є аудит використання ключа. Але ключ не надає клієнт у запиті.
- *Client-Side Encryption* — тоді шифрує не S3, а сам клієнт.
- *SSE-S3* — кожен об'єкт шифрується унікальним ключем, який шифрується ротованим master key; всім керує S3.

</details>

### T01-Q42
*домен: офіційна мітка*

> ⚠️ **KMS throttling: backoff + кешування data key.** → [детальніше](../../06-contradictions-and-traps.md#c11)

An e-commerce application posts its order transactions in bulk to an accounting application for further processing. Due to changes in the compliance rules, all the transactions are being encrypted with AWS Key Management Service (AWS KMS) key before posting to the accounting application. Post this change, the testers have raised tickets regarding the application receiving a ThrottlingException error.

What measures should a developer take to fix this issue MOST optimally? (Select two)

- ▫️ Use a bucket-level key for SSE-KMS which will decrease the requested traffic to AWS KMS thereby avoiding the ThrottlingException error
- ✅ Reduce the rate of requests and consider using the backoff and retry logic
- ▫️ Write queries in Amazon CloudWatch Logs Insights to track your API request usage and submit an AWS Support case to request a quota increase
- ✅ Use the data key caching feature with the AWS Encryption SDK encryption library
- ▫️ Send AWS CloudTrail events generated by AWS KMS to Amazon CloudWatch Logs

<details><summary>Пояснення</summary>

**✅ Правильні відповіді: «Reduce the rate of requests and consider using the backoff and retry logic» та «Use the data key caching feature with the AWS Encryption SDK»**

Кожен AWS SDK має автоматичні повтори, а також exponential backoff — дедалі довші паузи між повторами після послідовних помилок. Варто задати максимальну затримку і максимальну кількість повторів залежно від операції та умов (наприклад, мережевої затримки).

Data key caching зберігає data keys і пов'язаний криптоматеріал у кеші. При шифруванні чи розшифруванні Encryption SDK спершу шукає ключ у кеші й не генерує новий. Це підвищує продуктивність, знижує вартість і допомагає не виходити за ліміти сервісу. Кешування корисне, якщо ключі можна повторно використовувати, їх генерується дуже багато або криптооперації занадто повільні, дорогі чи обмежені. За замовчуванням SDK генерує новий ключ для кожної операції, тож кешування вмикають обережно, з пороговими значеннями безпеки.

**❌ Неправильні варіанти:**
- *Send CloudTrail events generated by KMS to CloudWatch Logs* — допоможе побачити throttled-виклики, але не виправить помилку.
- *Write CloudWatch Logs Insights queries and submit a Support case for a quota increase* — раніше так і робили, але тепер використання KMS API видно, а підвищення квоти запитується прямо в консолі Service Quotas.
- *Use a bucket-level key for SSE-KMS* — S3 у питанні не згадується.

Джерела: <https://docs.aws.amazon.com/general/latest/gr/api-retries.html> · <https://docs.aws.amazon.com/encryption-sdk/latest/developer-guide/data-key-caching.html> · <https://aws.amazon.com/blogs/security/manage-your-aws-kms-api-request-rates-using-service-quotas-and-amazon-cloudwatch/>

</details>

A developer is working on an application that must save hundreds of sensitive files. The application needs to encrypt each file using a unique key before storing it.

What should the developer do to implement this in the application?

- ✅ Use the AWS KMS GenerateDataKey API to acquire a data key, use the data key to encrypt the data, and store both the encrypted data key and the data.
- ▫️ Use a crypto library to generate a unique encryption key for the application, employ the encryption key to secure the data, and store the encrypted data.
- ▫️ Upload the data to an Amazon S3 bucket employing server-side encryption with a key from AWS KMS.

<details><summary>Пояснення</summary>

- *Upload to S3 with server-side encryption (KMS)* — за умовою дані треба шифрувати в застосунку до збереження.

Your development team uses the AWS SDK for Java on a web application that uploads files to several Amazon Simple Storage Service (S3) buckets using the SSE-KMS encryption mechanism. Developers are reporting that they are receiving permission errors when trying to push their objects over HTTP. Which of the following headers should they include in their request?

- ✅ 'x-amz-server-side-encryption': 'aws:kms'

### T04-Q53
*домен: визначено автоматично (у джерелі: AWS Security, Identity, & Compliance)*

An organization has encrypted a large quantity of data. To protect their data encryption keys they are planning to use envelope encryption. Which of the following processes is a correct implementation of envelope encryption?

- ✅ Encrypt plaintext data with a data key and then encrypt the data key with a top-level plaintext master key.
- ▫️ Encrypt plaintext data with a master key and then encrypt the master key with a top-level plaintext data key
- ▫️ Encrypt plaintext data with a master key and then encrypt the master key with a top-level encrypted data key
- ▫️ Encrypt plaintext data with a data key and then encrypt the data key with a top-level encrypted master key

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Encrypt plaintext data with a data key and then encrypt the data key with a top-level plaintext master key»**

Зашифровані дані захищені, але треба захищати й ключ шифрування. Envelope encryption: дані шифруються data key, а data key — іншим ключем. Ланцюжок може бути довшим, але ключ верхнього рівня має лишатися незашифрованим, щоб можна було розшифрувати решту; це **master key** (у KMS він ніколи не залишає сервіс). Переваги:
- **захист data keys** — зашифрований data key можна безпечно зберігати поруч із даними;
- **ті самі дані під кількома master keys** — перешифровуються лише data keys, а не великі дані;
- **поєднання алгоритмів** — швидкість симетричних і зручність керування асиметричними.

- *Encrypt data with a master key, then the master key with an encrypted data key* — та сама помилка ієрархії.

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Configure SSL certificates on an Elastic Load Balancer» + «Configure an Elastic Load Balancer with SSL termination»**

Трафік треба зашифрувати через HTTPS, а для цього потрібні SSL/TLS-сертифікати. Шифрування й розшифрування навантажують CPU, а EC2 і так перевантажені. Тому сертифікат ставлять на HTTPS listener балансувальника, і TLS термінується на ELB.

**❌ Неправильні варіанти:**
- *SSL pass-through* — TLS довелося б термінувати на EC2, а цього треба уникнути.
- *ELB with a KMS CMK* — KMS шифрує дані at rest, а не трафік.
- *Certificates on EC2* — ще більше навантажить CPU.

Джерела: <https://docs.aws.amazon.com/elasticloadbalancing/latest/application/create-https-listener.html>

</details>

### T11-Q55
*домен: офіційна мітка*

Which of the following best describes how KMS Encryption works?

- ▫️ KMS receives CMK from the client at every Encrypt call, and encrypts the data with that
- ✅ KMS stores the CMK, and receives data from the clients, which it encrypts and sends back
- ▫️ KMS generates a new CMK for each Encrypt call and encrypts the data with it
- ▫️ KMS sends the CMK to the client, which performs the encryption and then deletes the CMK

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «KMS stores the CMK, and receives data from the clients, which it encrypts and sends back»**

KMS-ключ (раніше CMK) — логічне представлення master-ключа: ID, дата створення, опис, стан і сам криптоматеріал. Його створюють у KMS, у кластері CloudHSM або імпортують. Типи:
- **симетричні** — 256-бітний ключ для шифрування і розшифрування;
- **асиметричні** — RSA (шифрування або підпис, але не обидва) чи ECC (підпис).

Власник: customer managed, AWS managed або AWS owned.

Огляд: https://docs.aws.amazon.com/kms/latest/developerguide/concepts.html#master_keys

⚠️ Твердження правдиве лише для даних до 4 KB. Більші дані шифрують через envelope encryption з data key. Див. 07.

**❌ Неправильні варіанти:**
- *Client sends CMK on every call* — ключ можна імпортувати лише один раз, а не передавати з кожним викликом.
- *KMS sends CMK to client* — KMS-ключ ніколи не покидає KMS.
- *New CMK for each call* — новий ключ на кожен виклик не створюється; є ротація ключів.

Джерела: <https://docs.aws.amazon.com/kms/latest/developerguide/concepts.html#master_keys> · <https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html>

</details>

- ▫️ Encryption by default is an AZ specific setting. If you enable it for an AZ, you cannot disable it for individual volumes or snapshots in that AZ
- ▫️ A snapshot of an encrypted volume can be encrypted or unencrypted
- ✅ A volume restored from an encrypted snapshot, or a copy of an encrypted snapshot is always encrypted

- *Snapshot of encrypted volume may be unencrypted* — завжди зашифрований.
- *AZ-specific setting* — налаштування регіональне, а не для AZ.

### T12-Q56

An e-commerce company has a fleet of EC2 based web servers running into very high CPU utilization issues. The development team has determined that serving secure traffic via HTTPS is a major contributor to the high CPU load.

Which of the following steps can take the high CPU load off the web servers? (Select two)

- ▫️ Create an HTTP listener on the Application Load Balancer with SSL pass-through
- ✅ Create an HTTPS listener on the Application Load Balancer with SSL termination
- ▫️ Create an HTTP listener on the Application Load Balancer with SSL termination
- ✅ Configure an SSL/TLS certificate on an Application Load Balancer via AWS Certificate Manager (ACM)
- ▫️ Create an HTTPS listener on the Application Load Balancer with SSL pass-through

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Create an HTTPS listener on the Application Load Balancer with SSL termination» + «Configure an SSL/TLS certificate on an Application Load Balancer via AWS Certificate Manager (ACM)»**

ALB розподіляє трафік між цілями в кількох AZ. Listener перевіряє запити на заданих протоколі й порту, а правила (пріоритет, дії, умови) визначають, куди їх спрямувати. Для HTTPS listener на балансувальнику потрібен щонайменше один SSL/TLS-сертифікат. ALB термінує TLS (SSL offload) і передає інстансам уже розшифровані запити. EC2 перевантажені за CPU, тож це знімає з них навантаження.

Як прив'язати сертифікат ACM до ALB чи NLB: https://aws.amazon.com/premiumsupport/knowledge-center/associate-acm-certificate-alb-nlb/

- *HTTPS listener with SSL pass-through* — розшифровувати однаково довелося б на EC2. До того ж ALB не підтримує pass-through; це можливо лише з NLB через TCP.
- *HTTP listener with SSL termination* — HTTP listener не працює з TLS.
- *HTTP listener with SSL pass-through* — HTTP listener не працює з TLS.

Джерела: <https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html> · <https://aws.amazon.com/premiumsupport/knowledge-center/associate-acm-certificate-alb-nlb/>

</details>
