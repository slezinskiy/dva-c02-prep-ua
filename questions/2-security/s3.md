### T01-Q13
*домен: офіційна мітка*

A media company wants to migrate a video editing service to Amazon EC2 while following security best practices. The videos are sourced and read from a non-public S3 bucket.

As a Developer Associate, which of the following solutions would you recommend for the given use-case?

- ▫️ Set up an IAM user with read-only permissions for the S3 bucket. Configure AWS credentials for this user via AWS CLI on the EC2 instance
- ▫️ Set up an S3 service role with read-only permissions for the S3 bucket and attach the role to the EC2 instance profile
- ▫️ Set up an IAM user with read-only permissions for the S3 bucket. Configure the IAM user credentials in the user data of the EC2 instance
- ✅ Set up an EC2 service role with read-only permissions for the S3 bucket and attach the role to the EC2 instance profile

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Set up an EC2 service role with read-only permissions for the S3 bucket and attach the role to the EC2 instance profile»**

Найкраща практика безпеки AWS — не створювати IAM-користувача для застосунку й не вбудовувати його облікові дані в код. Натомість створюють IAM-роль і прикріплюють до EC2-інстансу: застосунки на ньому отримують тимчасові облікові дані й можуть виконувати все, що дозволяють політики ролі. Тут потрібна роль з read-only доступом до бакета, прикріплена через instance profile.

**❌ Неправильні варіанти:**
- *IAM user … credentials via AWS CLI on the EC2 instance* та *IAM user … credentials in the user data* — передавати облікові дані користувача застосунку, вбудовувати їх у код чи прописувати в user data небезпечно.
- *S3 service role … attach to the EC2 instance profile* — застосунок працює на EC2, тож потрібна роль для сервісу EC2, а не S3.

</details>

### T01-Q23
*домен: офіційна мітка*

A company has a new media application that utilizes an Amazon CloudFront distribution that accesses the S3 bucket by using an origin access identity (OAI). The S3 bucket has an explicit access denial for all other users. A developer wants to allow access to the login page for unauthenticated users while ensuring the security of all private content that has restricted viewer access.

Which of the following will you recommend?

- ▫️ Configure a second cache behavior to the distribution having the same origin as the default cache behavior and have the path pattern for the second cache behavior as \* with viewer access as restricted. Modify the default cache behavior’s path pattern to the path of the login page and have the viewer access as unrestricted
- ▫️ Configure a new distribution having the same origin as the original distribution and set the path pattern for the default cache behavior of the new distribution as the path of the login page with viewer access as unrestricted. Keep the default cache behavior of the original distribution unchanged
- ✅ Configure a second cache behavior to the distribution having the same origin as the default cache behavior and have the path pattern for the second cache behavior as the path of the login page with viewer access as unrestricted. Keep the default cache behavior’s settings unchanged
- ▫️ Configure a second origin as the failover origin for the default behavior of the original distribution and have the path pattern for the second origin as the path of the login page with viewer access as unrestricted. Keep the behavior for the primary origin unchanged

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Configure a second cache behavior … same origin as the default cache behavior … path pattern as the path of the login page with viewer access unrestricted. Keep the default cache behavior's settings unchanged»**

Cache behavior визначає, як CloudFront обробляє запити. Кожен behavior задає один origin, з якого CloudFront бере об'єкти. Path pattern (наприклад, `images/*.jpg`) визначає, до яких запитів застосовується behavior. Шлях запиту порівнюється з pattern'ами в порядку, в якому behaviors перелічені в distribution. Pattern default cache behavior завжди `*` і змінити його не можна; якщо запит не підійшов жодному pattern'у, діє default.

Тож треба додати другий cache behavior з тим самим origin і поставити його вище default. Його path pattern — шлях сторінки логіну, а доступ — unrestricted. Так неавтентифіковані користувачі отримають доступ до сторінки логіну, а налаштування default behavior лишаться без змін, і весь приватний контент і далі буде захищений.

**❌ Неправильні варіанти:**
- *Змінити path pattern default behavior на шлях логіну* — неможливо: для default behavior pattern завжди `*`.
- *Створити нову distribution з тим самим origin…* — так задачу правильно не вирішити: потрібен лише додатковий cache behavior у наявній distribution.
- *Додати другий origin як failover…* — origin failover (origin group: primary + secondary) спрацьовує лише тоді, коли primary недоступний або повертає певні коди помилок. Тож сторінка логіну і решта контенту ніколи не працюватимуть разом.

Джерела: <https://docs.aws.amazon.com/cloudfront/latest/APIReference/API_CacheBehavior.html> · <https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/high_availability_origin_failover.html>

</details>

### T01-Q51
*домен: офіційна мітка*

A financial services company uses Amazon S3 to store transformed and anonymized customer data that is generated by a daily batch job. The development team has been tasked to build a solution that analyzes the output of the daily job for any sensitive financial information about the company's customers.

As an AWS Certified Developer Associate, which of the following options would you recommend to address this use case MOST efficiently?

- ✅ Leverage Macie to analyze the output of the daily batch job and look for any sensitive data findings of type SensitiveData:S3Object/Financial
- ▫️ Leverage Macie to analyze the output of the daily batch job and look for any sensitive data findings of type SensitiveData:S3Object/CustomIdentifier
- ▫️ Leverage Macie to analyze the output of the daily batch job and look for any sensitive data findings of type SensitiveData:S3Object/Personal
- ▫️ Configure a S3 event notification for every object upload that triggers a Lambda function based Python script to detect sensitive customer information

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Leverage Macie to analyze the output of the daily batch job and look for any sensitive data findings of type SensitiveData:S3Object/Financial»**

Amazon Macie — сервіс безпеки даних, що за допомогою машинного навчання і зіставлення шаблонів знаходить чутливі дані, показує ризики та автоматизує захист. Macie веде інвентар S3-бакетів, оцінює їхню безпеку й контроль доступу і створює finding, коли бачить проблему (наприклад, бакет став публічним). Також він знаходить чутливі дані в об'єктах — за вбудованими або власними критеріями — і генерує sensitive data finding. Тип `SensitiveData:S3Object/Financial` означає, що об'єкт містить фінансову інформацію: номери банківських рахунків чи кредитних карток.

**❌ Неправильні варіанти:**
- *…SensitiveData:S3Object/Personal* — це про персональні дані (адреси, номери посвідчень) і медичну інформацію, а не фінансову.
- *…SensitiveData:S3Object/CustomIdentifier* — збіг із власними (custom) ідентифікаторами.
- *S3 event notification + Lambda-застосунок для пошуку чутливих даних* — підтримувати власний детектор неефективно: його треба постійно оновлювати під нові формати. Macie робить це краще.

Джерела: <https://docs.aws.amazon.com/macie/latest/user/what-is-macie.html> · <https://docs.aws.amazon.com/macie/latest/user/findings-types.html>

</details>

What solution will fulfill these criteria?

- ▫️ Enable the Amazon S3 Transfer Acceleration feature to ensure encryption during transit.

*домен: офіційна мітка*

You have a popular web application that accesses data stored in an Amazon Simple Storage Service (S3) bucket. Developers use the SDK to maintain the application and add new features. Security compliance requests that all new objects uploaded to S3 be encrypted using SSE-S3 at the time of upload. Which of the following headers must the developers add to their request?

- *'SSE-S3'* і *'SSE-KMS'* — назви опцій, а не допустимі значення заголовка.
- *'aws:kms'* — валідне значення, але для SSE-KMS (коли потрібен контроль над ключами: створення, ротація, вимкнення). А тут вимога — SSE-S3.

</details>

You are storing your video files in a separate S3 bucket than your main static website in an S3 bucket. When accessing the video URLs directly the users can view the videos on the browser, but they can't play the videos while visiting the main website.

What is the root cause of this problem?

A company developed an app-based service for citizens to book transportation rides in the local community. A new feature has been requested where receipts would be emailed to customers with PDF attachments retrieved from Amazon Simple Storage Service (S3).

A developer has an application that stores data in an Amazon S3 bucket. The application uses an HTTP API to store and retrieve objects. - ✅ Invoke the PutObject API operation and set the x-amz-server-side-encryption header as AES256. Use an S3 bucket policy to deny permission to upload an object unless the request has this header
- ▫️ Set the encryption key for SSE-S3 in the HTTP header of every request. Use an S3 bucket policy to deny permission to upload an object unless the request has this header

<details><summary>Пояснення</summary>

**✅ Правильна відповідь: «Invoke the PutObject API operation and set the x-amz-server-side-encryption header as AES256. Use an S3 bucket policy to deny permission to upload an object unless the request has this header»**

SSE-S3 захищає дані at rest: кожен об'єкт шифрується унікальним ключем, а ці ключі — master-ключем, який S3 регулярно ротує. Шифр — AES-256. Для SSE-S3 значення заголовка `x-amz-server-side-encryption` — `AES256`.

```json

      "Action": "s3:PutObject", "Resource": "arn:aws:s3:::DOC-EXAMPLE-BUCKET/*",
      "Condition": { "StringNotEquals": { "s3:x-amz-server-side-encryption": "AES256" } } },
    { "Sid": "DenyUnencryptedObjectUploads", "Effect": "Deny", "Principal": "*",
      "Action": "s3:PutObject", "Resource": "arn:aws:s3:::DOC-EXAMPLE-BUCKET/*",
      "Condition": { "Null": { "s3:x-amz-server-side-encryption": "true" } } } ] }
```

- *Header = aws:kms* — це значення для SSE-KMS, а потрібен SSE-S3.
- *Header = sse:s3* — такого значення не існує.
- *Set SSE-S3 key in the header* — ключ SSE-S3 недоступний клієнту; власний ключ передають лише в SSE-C.
